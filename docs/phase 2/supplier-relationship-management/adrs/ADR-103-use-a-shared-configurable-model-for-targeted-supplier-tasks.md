# ADR-103: Use a Shared Configurable Model for Targeted Supplier Tasks

## Context and Problem Statement

Supplier-facing work currently appears in several forms: one-time requests, recurring record uploads, checklist-based confirmations, testing obligations, surveys, and process-specific project tasks. Rebuilding the same assignment, completion, review, notification, and reporting behavior for every use case would fragment supplier work and preserve email-based activity that is not traceable in Intelex.

Targeted requests to one supplier and campaign requests to many suppliers have different initiation patterns, but their resulting work items share common behavior. PPAP-generated project tasks also need to remain distinguishable from post-PPAP or relationship-management obligations even when both use similar controls.

## Decision Drivers

- Reuse assignment, completion, review, recurrence, and reporting behavior.
- Route work to maintained supplier roles rather than named individuals.
- Support completion notes, file uploads, and governed checklists.
- Allow one-time and frequency-driven obligations.
- Preserve supplier, part, drawing, and originating-process traceability where applicable.
- Keep targeted tasks distinct from multi-supplier campaigns and PPAP child elements.
- Prevent later template changes from altering active or historical task instances.

## Considered Options

### Build a separate object and workflow for every request type

Provides purpose-specific forms but duplicates common logic and fragments reporting.

### Use supplier surveys for every supplier request

Reuses campaign behavior but is awkward for targeted part- or drawing-specific obligations and one-off requests.

### Use one shared configurable supplier-task model with distinct initiation patterns

Reuses common task behavior while allowing targeted tasks, recurring obligations, and campaign-generated instances to retain their business context.

## Decision Outcome

Propose a shared supplier-task model for targeted requests and for the supplier-scoped work items generated by campaigns. Every task is related to a supplier and assigned to a maintained supplier role. A task may optionally relate to a canonical part, and when part context is present it may also identify the applicable drawing.

Task configuration defines whether the task is one-time or frequency-driven; whether completion requires a note, one or more file uploads, or a governed checklist; and whether supplier completion closes the task or routes it to an internal role for review. Targeted tasks are created for one supplier and business context at a time. Campaigns governed by ADR-080 define common properties once and generate one supplier-scoped task instance for each selected supplier.

Reusable task templates may predefine completion controls, checklist, routing, and reporting classification. Truly one-off tasks may be configured without a template, but an ad hoc task cannot introduce an ad hoc checklist. A checklist must come from governed configuration.

When a task instance is created, snapshot the applicable template and checklist version. Later template changes apply only to new instances unless an explicit governed migration is performed.

PPAP child elements remain governed by ADR-022. A PPAP may create a related supplier task for an ongoing obligation, but that task is not part of the PPAP completion structure.

The shared task pattern does not replace domain records whose business lifecycle is already distinct, including Warranty Analysis under ADR-059 and event-driven Supplier Lot Approval under ADR-085. Those applications may reuse task behavior only where their own ADRs permit it. Likewise, ADR-017 does not require native recurrence inside APQP merely because a shared supplier-task capability exists.

## Consequences

### Positive

- Gives suppliers and internal users one consistent task interaction pattern.
- Reuses reminders, review, recurrence, and completion reporting.
- Replaces informal email requests with traceable records.
- Supports part- and drawing-level retrieval of recurring evidence.
- Templates improve consistency without preventing exceptional one-off requests.

### Negative

- A highly reusable task object requires careful type-specific forms and filtering.
- Cross-application ownership and navigation may be less obvious than dedicated objects.
- Template, checklist, and role governance become shared operational responsibilities.

### Follow-up and Constraints

- Confirm whether targeted tasks and campaign-generated tasks use one physical base object or aligned application-specific objects.
- Define recurrence, reminder, escalation, cancellation, and reassignment behavior.
- Define the internal reviewer role for each governed template.
- Confirm which Supplier Scorecard and APQP use cases should use this model.
- Provide consolidated supplier-profile views without exposing internal-only work.
