# PPAP baseline change impact and reuse contract

**Status:** Proposed target change-impact specification aligned to the retained-object target architecture. Baseline facts are Extracted. Prepared 2026-11-17. No tenant configuration was changed.

This appendix gives every existing PPAP and inherited Project Abstract field an explicit disposition. The original baseline remains [baseline-model.json](../ootb-ppap-baseline-model/baseline-model.json), [OOTB technical specification](../ootb-ppap-baseline-model/ppap-ootb-technical-specification.md), [workflow automation](../ootb-ppap-baseline-model/workflow-automation.md), and [views/security evidence](../ootb-ppap-baseline-model/security-seeds-views.md). Current requirements are the 42 confirmed decisions in [target-requirements-decisions.json](../target-requirements-decisions.json); superseded PPAP-EVIDENCE-003 is excluded. Architecture is in the [target technical specification](ppap-target-technical-specification.md), canonical fields in the [target field contract](ppap-target-field-contract.md), and structure in the [target object model](ppap-target-object-model.md). This appendix records change history/impact and does not redeclare target fields.

## 1. Smallest coherent reuse boundary

**Extracted:** PPAP is concrete despite internal name `APQP_PPAPAbstractObject`; GUID `a99ca3b8-48ed-43eb-9696-a1dd26122c39`, main package `/GraphData/Items/45`, `IsAbstract=false`, `HasWorkflow=true`, `IsAuditEnabled=false`, `IsSecurityEnabled=false`. It directly inherits `ProjectFwk_ProjectAbstractObject`, GUID `89351fdb-6445-4899-86da-d888a1787563`, `/GraphData/Items/6`. Direct inheritance evidence: main package `/GraphData/Items/379/GraphData/Relations/24` and `/GraphData/Relations/284`; data package `/GraphData/Relations/1444`. APQP (`f03e2731-655c-4af2-9c84-d3035e3fc61a`, `/GraphData/Items/9`) shares the base.

**Proposed:** retain object identity and direct inheritance. Assign a new PPAP-only workflow to target new records through a verified tenant binding; do not rewrite historical workflow instances. Stages are Draft / In Progress / Management Review; Approved and Cancelled are termination outcomes. Explicit Complete PPAP validates the package and either completes non-safety PPAP or enters Management Review for important-safety PPAP. Return for More Information goes to In Progress and remains internal. No interim/conditional approval.

Add dedicated **PPAP Part**, **PPAP Shipping Depot**, **PPAP Element** (standalone native workflow), **PPAP Evidence Snapshot**, **PPAP Requirement/Version**, and **PPAP Template/Version** structures. Add authoritative drawing/revision, **Manufacturing Facility**, governing context and issuance fields to PPAP. These structures have distinct junction attributes, reviewed-work lifecycles, immutable evidence or published-configuration responsibilities not established by shared Project Framework. Reuse native audit, workflow, reminder and notification evidence before adding custom evidence objects.

Do not change targets or meaning of inherited Product (single Item Revision), Supplier (Public Profile), Location (platform Location), ProjectTemplate or ProjectTasks. These remain compatibility context; they do not establish drawing/facility/selected-parts scope or reviewed element completion. Target PPAP must not require a surrogate Product or dummy legacy Project Template to satisfy obsolete form rules.

**Proposed branch guard:** PPAP.`Target Configuration?` is system-managed, FALSE for existing/historical records, TRUE only through target creation, then locked. Preserve APQP and historical PPAP branches. Shared Project Abstract handlers require a tenant-verified typed resolution of the PPAP-only guard: do not assume base-object formulas can directly address a descendant field or invent subtype functions. Initialize the guard before shared Create handlers execute. If type resolution/ordering cannot be proved, target workflow binding remains a release gate; a null/unmapped target identity cannot silently enter legacy generation.

**Extracted compatibility:** retain `PPAP.Task` -> `ProjectFwk_TaskObject` (`04b40719-eb5d-4202-9811-60b039739c78`, `/GraphData/Items/236`), inverse Integrated Task.PPAPs; retain `APQP_APQPObject.PPAPAbstract` -> PPAP (`dfb50215-0b52-4c99-8278-6dde82e68c9f`, `/GraphData/Items/620`), inverse PPAP.APQPAbstract. These are associations, not inheritance. APQP task may initiate/source-link a target draft; only target validation/issue establishes authoritative scope. Approval may fulfil linked work; cancellation exposes a separate unresolved outcome.

Rejected alternatives: globally retype shared Product/Supplier/Location (breaks APQP); silently reparent PPAP (loses inherited contracts and integration expectations); use one Item Revision for a selected drawing-part set (incorrect approval scope); use generic Task/Checklist completion for engineer approval (changes shared consumer semantics). A separate replacement PPAP object adds a wider compatibility bridge without a named requirement.

## 2. All existing field dispositions

Field/type/required/read-only/GUID/pointer columns below are **Extracted**; target disposition/behavior is **Proposed**. Pointers are JSON pointers within `APQP & PPAP Manager(v1.0.0.0).ipack` unless stated otherwise. GUID resolves the declaration in baseline JSON. R/O is exported metadata, not effective authorization; required Y/N is object metadata, distinct from create-view/target issue gates. Full defaults/calculations/inverses remain in baseline JSON.

Retire or Remove active target use removes the field from new target capture, formulas, automation, notifications and reporting; historical schema/data/baseline evidence remain. This does not authorize destructive metadata deletion or migration. Conditional legacy warrant reuse remains pending PPAP-INPUT-001 reconciliation; no field becomes a required target gate merely because OOTB had it. Final target contracts either define accepted reuse or omit retired fields; this impact appendix retains names for traceability.

## 5. Cancellation-as-success removal and historical compatibility

**Extracted defect against target requirements:** Auto Close Related Task WF treats Cancelled exactly like Completed and sets linked task complete. OOTB Reject uses workflow cancel, so rejected PPAP can satisfy an integrated task. Target PPAP-LIFECYCLE-002 explicitly prohibits that result.

**Proposed ordered target cancellation contract:**

1. Current responsible engineer or designated PPAP administrator invokes Cancel PPAP while issued/open; validate authorization and mandatory reason before mutation. Closed Approved is ineligible.
2. Preserve source context, issued scope/baselines, workflow history, all submissions/approved/rejected evidence, copied-from links, metric facts and posted discussions. Stamp authenticated actor and timezone-enabled cancellation time through native workflow/audited target metadata.
3. Cancel only outstanding element work and stop its reminders/actions; leave already completed/approved evidence records unchanged as historical facts. Stop PPAP review/reminder work. Enforce post-closure discussion read-only.
4. Record cancelled outcome for PCR/APQP interface with the specific originating PPAP identity and flag responsible owner resolution. Do not cancel entire originating process, complete linked work, stamp a successful completion, or issue an approval certificate.
5. Terminate PPAP Cancelled only when required cascade/link effects are durably successful. Partial failure remains visible to owning operation/native execution evidence; retry resumes idempotently without duplicate notices or losing actor/reason, and cannot leave an apparently completed cancellation with still-active element work.
6. Exclude approved snapshots whose source PPAP is now cancelled from future suggestions/reuse. Previously copied immutable snapshots in other PPAPs remain unchanged. Preserve previous first-complete-submission timeliness facts; pre-submission cancelled work is excluded from denominator and cancellation is reported separately.

Target success processing is a distinct path after actual Approved commit; it rechecks originating task/scope and open-work eligibility, does not reopen closed tasks, and is retry-safe. Never implement target cancellation by calling the legacy DateNotRequired closure path. Historical workflow/schema evidence is preserved; no active/historical legacy workflow migration is authorized under PPAP-MIGRATION-001.
