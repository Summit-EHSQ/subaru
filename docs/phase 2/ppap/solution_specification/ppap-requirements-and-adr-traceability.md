# PPAP target requirements and ADR traceability

This register applies to the proposed first-release target, dated 2026-11-17. It records design coverage, not implemented or tested behavior. The separate [OOTB baseline](../ootb-ppap-baseline-model/ppap-ootb-technical-specification.md) remains unchanged.

## 1. Authority and reading rules

1. The 42 current confirmed records in [target-requirements-decisions.json](../target-requirements-decisions.json) govern. `PPAP-EVIDENCE-003` is superseded and is not a current requirement.
2. Apply the current decision outcome of each PPAP ADR and the authoritative adjacent-domain ADRs where compatible with those user decisions. An ADR filename, title, accepted status, or earlier option does not override a subsequent confirmed correction.
3. Use [solution-brief.md](../solution-brief.md) as explanatory context after applying those corrections. In particular, its engineering-change absorption wording is historical.
4. The OOTB packages establish the extracted baseline. They do not establish the final SIA requirement matrix. Target additions and modifications are proposed logical configuration until tenant implementation proves them.

The model concepts below identify responsibility rather than promise a physical table or particular platform API. The [target technical specification](ppap-target-technical-specification.md) coordinates the [canonical field contract](ppap-target-field-contract.md) and [object model](ppap-target-object-model.md). Names include PPAP Part, PPAP Shipping Depot, PPAP Element, PPAP Evidence Snapshot, PPAP Requirement / PPAP Requirement Version, PPAP Template / PPAP Template Version, PPAP Model Change, PPAP Model Date, PPAP Build Event, PPAP Engineering Release, PPAP Drawing Review, PPAP Discussion Thread and PPAP Discussion Post. Existing PPAP behavior is guarded by `Target Configuration?`; dedicated target objects and native workflows avoid shared APQP schema mutation. [Acceptance scenarios](ppap-acceptance-scenarios.md) use stable `AC-01` through `AC-56` identifiers.

**Coverage status:** `Satisfied` means the proposed design and acceptance contract express the decision; it does not mean runtime acceptance passed. `Partially satisfied` means the governing rule is specified but a named interface or configuration detail remains outstanding. `Blocked` means source-backed configuration cannot be completed without the named input. Runtime proof is a separate gate for every row.
